# ADR-0011: E2E テストツールに Maestro を採用する

- **ステータス**: Accepted
- **日付**: 2026-08-18
- **決定者**: Claude（Phase 6 / 設計）

## 背景

[`repository-structure.md`](../repository-structure.md) で「Maestro もしくは Detox、Phase 6 で選定」
としていた E2E ツールを確定する。

前提:
- アプリは Expo（Development Build が必要なネイティブモジュールを含む）
- モックを使わないため、E2E は実 Supabase・実 Gemini に接続する（[ADR-0006](./0006-no-mocks-testing-policy.md)）
- 主要な操作要素には設計段階から `testID` を付けてある（[`../frontend/screens.md`](../frontend/screens.md)）

## 選択肢

1. **Maestro** — YAML でフローを書く。アプリ側の変更は不要
2. **Detox** — JS でテストを書くグレーボックス方式。アプリのビルドにテスト用の設定を組み込む
3. E2E を書かず、手動確認のみ

## 決定

**Maestro を採用する。** Android エミュレータ上での実行を CI の対象とし、
iOS は手元の Simulator / 実機での確認に委ねる。

## 理由

- **アプリのコードとビルド設定を変えずに導入できる。** Detox はテスト用のビルド構成
  （`detox.config.js`、ネイティブ側の設定）を継続的に維持する必要がある。
  MVP の規模に対してこの維持コストは重い。
- **Detox の主な利点が、このアプリでは効かない。** Detox の強みは
  アニメーションや非同期処理の完了を自動で待つ同期制御にあるが、
  本アプリの画面はアニメーションをほとんど持たない。
  待ちが必要なのは「LLM の応答」で、これは Maestro の
  `extendedWaitUntil` で十分扱える。
- **フローが読める。** YAML なので、実装者以外（オーナー）が
  「何を確認しているのか」を追える。仕様の合意にも使える。
- 選択肢3（手動のみ）は、契約の不整合（[ADR-0002](./0002-shared-types-deferred.md) で
  共通型を持たないと決めた分のリスク）を実際に検出する手段がなくなるため採らない。

## 影響

- **Google / Apple ログインは E2E の対象外になる。** これらは外部（Google/Apple）の
  認証画面を自動操作することになり、先方の UI 変更でテストが壊れる。
  壊れやすいテストは、失敗が信用されなくなり結局無視されるため置かない。
  → 手動確認のチェックリストとして [`../testing/e2e-strategy.md`](../testing/e2e-strategy.md) に残す。
- **サインアップも対象外。** メール確認が有効なため受信箱の操作が必要になる。
  テスト用ユーザーは Admin API で確認済み状態として事前作成する。
- **iOS の E2E は CI で回さない。** macOS ランナーの課金係数（Linux の10倍）に対して、
  得られる情報が Android での実行と大きく変わらない。
  ただし **Apple ログインと SecureStore の挙動は iOS 固有**なので、
  リリース前の手動確認を必須とする。
- 再検討のトリガー:
  - 画面にアニメーションや複雑な非同期遷移が増え、待ち時間の調整が頻発するようになった
  - E2E が「たまに落ちる」ようになり、原因が同期制御にあると判明した
