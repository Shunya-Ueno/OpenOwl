# ADR-0008: 生成結果は全ユーザー横断のキャッシュとして共有する

- **状態**: Accepted
- **日付**: 2026-08-22
- **フェーズ**: 2

## 背景

DeepSeek API は従量課金で、呼び出し回数がそのままコストになる。
語学学習アプリでは、ユーザー間で検索される単語が高い確率で重複する
（頻出語・教材に出てくる語に集中する）。
一方で「誰が何を検索したか」はユーザー固有の情報であり、他人に見せてはならない。

## 決定

データを 2 種類に分ける。

- **共有データ**（`terms` / `synonym_generations` / `synonym_items`）
  … ユーザー ID を持たない。全ユーザーで共有され、キャッシュとして再利用される。
- **ユーザー固有データ**（`lookups`）
  … 「誰が」「いつ」「どの語を」引いたかの記録。RLS で本人のみに限定する。

同一の `(term, model, prompt_version)` に対する生成結果が TTL（既定 30 日）以内に
存在すれば、DeepSeek を呼ばずにそれを返す。

## 理由

- **コスト削減が直接的**。2 人目以降の同じ単語は課金ゼロになる。
  語彙の分布を考えると、この重複率は無視できない大きさになる。
- **類義語というデータは陳腐化しにくい**。「improve の類義語」は
  時間が経っても変わらない。キャッシュの鮮度リスクが小さいドメインである。
- **レイテンシも改善する**。キャッシュヒット時は DB アクセスのみで応答できる。
- **障害時の縮退応答に使える**。DeepSeek が落ちていても、
  TTL 切れのキャッシュを `stale: true` として返せる。
  エラー画面より明らかに有用。
- 共有するのは辞書的知識のみで、個人情報を含まない。
  「誰が引いたか」は `lookups` に分離されているため、共有しても漏れない。

## 検討したが採用しなかった案

| 案 | 却下理由 |
| --- | --- |
| ユーザーごとに生成結果を保存（共有しない） | 同じ単語で人数分の課金が発生する。設計上の利点がない |
| キャッシュしない（毎回生成） | コスト・レイテンシとも最悪。多様性が必要なタスクでもない |
| Deno KV / 外部キャッシュを使う | 既に Postgres がある。永続化と履歴表示に同じデータが必要なので、DB に置くのが自然 |
| TTL なし（永久キャッシュ） | プロンプト改善やモデル更新の成果が反映されなくなる。`prompt_version` と TTL の両方で更新経路を確保する |

## 結果 / 影響

- `terms` / 生成結果テーブルは `user_id` を持たない。
- これらのテーブルの RLS は「自分が引いたことのある語のみ SELECT 可」とする。
  個人情報ではないが、全開放すると「全ユーザーの検索傾向」という別種の情報になるため。
- 書き込みは Edge Function の `service_role` のみが行う。
- ユーザーが明示的に「別の候補を見る」を選んだ場合のみ `forceRefresh: true` で再生成する。
- プロンプトを変更したら `prompt_version` を上げる。これによりキャッシュが自然に無効化される。
