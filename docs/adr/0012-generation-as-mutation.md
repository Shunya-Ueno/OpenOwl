# ADR-0012: 類義語生成は mutation として扱い、URL 直接アクセスでは再生成しない

- **状態**: Accepted
- **日付**: 2026-08-22
- **フェーズ**: 4

## 背景

類義語生成は「単語を渡すと結果が返る」形をしており、一見 `useQuery` で表現できる。
しかし実際には DeepSeek への課金が発生し、ユーザーごとのレート制限
（1 時間 60 回）を消費する副作用付きの操作である。

さらに `/synonyms/[word]` を独立ルートにした結果
（[`frontend-design.md`](../frontend-design.md) §2.1）、
URL 直接アクセス・リロード・履歴からの遷移という「ユーザーが生成ボタンを押していない」
到達経路が生まれた。

## 決定

1. **生成は `useMutation` で表現する。`useQuery` を使わない。**
2. **URL 直接アクセス時は生成しない。** PostgREST から自分の過去の結果を読み、
   無ければ「この単語を生成する」ボタンを表示して明示的な操作を求める。
3. mutation の `retry` は `false` にする。

## 理由

- `useQuery` はウィンドウフォーカス復帰・再マウント・ネットワーク再接続で
  **自動的に再取得する**。これは「ユーザーが押していないのに課金が発生する」ことを意味する。
  PWA ではタブ切り替えが日常的に起きるため、実害が出る確率が高い。
- 同じ理由で、`retry` によるリトライも自動課金になる。サーバー側は既に
  リトライを最大 1 回に絞ってコストを制御しており（[`llm-integration.md`](../llm-integration.md) §5.1）、
  クライアントが上からさらに再送すればその制御が無意味になる。
- URL を開くだけで課金が発生する状態は、リンクを踏んだだけのユーザーにとって予測不能。
  「押したら生成される」という因果をユーザーに見せる方が、コスト面でも UX 面でも正しい。
- 過去の結果を読む経路は既にある（[ADR-0009](./0009-read-path-via-postgrest.md) の PostgREST 直読み）。
  追加のサーバー実装なしで実現できる。

## 検討したが採用しなかった案

| 案 | 却下理由 |
| --- | --- |
| `useQuery` + `staleTime: Infinity` + `refetchOnWindowFocus: false` | 自動再取得を全部個別に無効化することになる。既定が危険側に倒れている道具を使うより、意味の合う道具（mutation）を使う方が事故が少ない |
| URL 直接アクセス時に自動生成する | リンクを踏んだだけで課金。レート制限も消費する |
| 結果をホーム画面にインライン表示し、独立ルートを作らない | リロードで結果が消え、ブラウザバックがアプリの外に出る。PWA として不自然（§2.1） |

## 結果 / 影響

- 結果画面は「mutation の結果を受け取った場合」と「保存済みを読んだ場合」の
  2 つの入力を扱う。どちらも同じ表示コンポーネントに渡せるよう、
  ドメイン表現（`SynonymResult`）に正規化してから渡す。
- 「別の候補を見る」（`forceRefresh: true`）も当然 mutation。既定で `true` にしない。
- 生成成功時は履歴クエリを `invalidateQueries` する。
