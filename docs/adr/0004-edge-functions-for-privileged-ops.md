# ADR-0004: Edge Functions は特権操作のみ。読み取りは PostgREST + RLS を使う

- **ステータス**: Accepted
- **日付**: 2026-08-16
- **決定者**: Claude（設計フェーズ / Opus）

## 背景

Supabase では、クライアントから Postgres に直接（PostgREST 経由で）問い合わせる方法と、
Edge Functions に API を作る方法の両方が使える。
どの操作をどちらに寄せるかの方針を決めないと、
「なんとなく Function を作る」ことになり、実装量とレイテンシと運用対象が増える。

## 選択肢

1. **全操作を Edge Functions 経由にする**（従来の REST API サーバに近い形）
2. **全操作をクライアントからの直接クエリにする**（LLM 呼び出しも含む）
3. **特権が必要な操作のみ Edge Functions、それ以外は PostgREST + RLS**

## 決定

**選択肢3**。Edge Functions を作るのは、次のいずれかに該当する操作のみとする。

- サーバ側の秘密（`GEMINI_API_KEY`、service_role key）が必要
- クライアントに任せると信頼性が壊れる制御（レート制限、キャッシュ判定、利用量記録）
- 複数テーブルにまたがる原子的な書き込み

MVP ではこれに該当するのは `generate-synonyms` の1本だけ。
検索履歴・プロフィールの読み取りは PostgREST への直接クエリで行う。

## 理由

- **選択肢2は不可能。** Gemini API キーをクライアントに置くことになり、要件に反する。
- **選択肢1は割に合わない。** 履歴取得のような単純な読み取りに Function を挟むと、
  コールドスタート分のレイテンシ、実装・テスト対象、デプロイ対象が増える。
  一方で得られる安全性は RLS と変わらない（**認可の根拠はどちらの経路でも RLS**）。
- PostgREST は join・フィルタ・ページングを標準で備えており、
  履歴画面に必要なクエリを追加実装なしで賄える。
- 「Function を作る基準」を明文化しておくことで、将来機能（単語帳など）で
  安易に CRUD エンドポイントが増えるのを防げる。

## 影響

- **RLS の設計品質がそのままセキュリティの品質になる。**
  RLS の検証（[`security.md`](../security.md#rls-の検証phase-3-の完了条件)）を実装フェーズの完了条件に含める。
- クライアントは DB のテーブル構造に依存する。スキーマ変更時はフロント側の追随が必要になるため、
  変更は同一 PR で行う。
- 将来の単語帳機能（自分のデータの CRUD）も Edge Function を作らず、RLS 付きの直接クエリで実装する見込み。
- 例外的に Function が必要になる将来の操作: アカウント削除（`auth.admin` API が必要）、
  例文生成・会話（LLM キーが必要）。
