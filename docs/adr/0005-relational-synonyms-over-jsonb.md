# ADR-0005: 類義語をリレーショナルに保存する（jsonb 単一カラムにしない）

- **ステータス**: Accepted
- **日付**: 2026-08-16
- **決定者**: Claude（設計フェーズ / Opus）

## 背景

Gemini から返る類義語（5件程度、それぞれに品詞・語義・ニュアンスを持つ）をどう保存するか。
MVP の画面はリストを表示するだけなので、`jsonb` 1カラムでも要件は満たせる。

## 選択肢

1. **`synonym_generations.result jsonb` に配列ごと格納する**
2. **`synonyms` テーブルに1件1行で格納する**

## 決定

**選択肢2**。`synonyms` テーブルを作り、1類義語 = 1行で保存する。

## 理由

- **将来の単語帳が「特定の類義語」を指す必要がある。**
  「`joyful` を単語帳に追加」という操作は、`vocabulary_entries.synonym_id` のような
  外部キーで表現するのが自然。`jsonb` 内の要素は FK で指せないため、
  配列インデックスを保存するような壊れやすい参照になる。
  これは MVP 直後に来る機能なので、YAGNI の例外として先に払っておく価値がある。
- **DB レベルで妥当性を保証できる。** 文字数・品詞の列挙・表示順の一意性を
  CHECK / UNIQUE 制約で表現できる。`jsonb` だとアプリ側の検証だけが頼りになる。
- **集計しやすい。** 「よく提示される類義語」「同じ語が複数の単語の類義語として出る」といった
  分析が普通の SQL で書ける。
- 追加コストは小さい。テーブル1つ、行数は生成1回あたり5行程度。

## 影響

- 書き込みが `synonym_generations` と `synonyms` の2テーブルにまたがるため、
  **原子性の担保が必要**になる。PostgREST の複数リクエストは別トランザクションになるため、
  `record_synonym_generation` という Postgres 関数にまとめて呼ぶ
  （[`db-schema.md`](../db-schema.md#生成結果を原子的に保存する-rpc)）。
  これを怠ると「類義語0件の生成記録」がキャッシュとして残り、
  以後その単語が永久に空の結果を返す。
- 読み取りは join が1つ増えるが、`(generation_id, sort_order)` のインデックスで十分に速い。
- **一方で `synonyms.term` から `words` への FK は張らない。**
  類義語ごとに `words` 行を作ると、検索されていない単語で辞書が膨らむ。
  こちらは実際に必要になってから追加する（YAGNI を適用する側）。
