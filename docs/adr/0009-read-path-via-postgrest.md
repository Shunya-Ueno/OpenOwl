# ADR-0009: 読み取り系 API を作らず、PostgREST を直接使う

- **状態**: Accepted
- **日付**: 2026-08-22
- **フェーズ**: 2

## 背景

検索履歴の取得やプロフィールの参照について、Edge Function を用意するか、
クライアントから Supabase の PostgREST（`supabase.from(...)`）を直接呼ぶかを決める必要がある。

## 決定

**外部 API 呼び出しやシークレットを伴う書き込みのみ Edge Function とする。**
読み取り（履歴一覧、プロフィール）と単純な削除・更新は PostgREST を直接使う。
結果として MVP の Edge Function は `POST /synonyms` の 1 本のみになる。

## 理由

- **RLS が既に認可を担保している。** 履歴取得のために Edge Function を挟んでも、
  やることは「RLS が返す行をそのまま転送する」だけで、価値を足していない。
- **層を足すとコストが増える。** エンドポイントが増えれば、認証処理・CORS・
  エラーハンドリング・型定義・デプロイ対象がその数だけ増える。
- **クライアント側で必要な形が変わりやすい。** 履歴画面の表示項目はフェーズ 4 で
  変わりうる。PostgREST の `select` なら、サーバーを再デプロイせずに
  取得する列とネストを変えられる。
- **Edge Function を置くべき明確な理由がある操作は限られている**:
  シークレットの秘匿（DeepSeek キー）、外部 API 呼び出し、
  複数テーブルへの原子的な書き込み、レート制限。
  読み取りはどれにも該当しない。

## 検討したが採用しなかった案

| 案 | 却下理由 |
| --- | --- |
| すべて Edge Function 経由にする | RLS があるのに認可を二重実装することになる。エンドポイント数だけ保守対象が増える |
| すべて PostgREST 直接にする | DeepSeek のキーを秘匿できない。成立しない |
| GraphQL を導入する | クエリが数種類しかなく、導入コストに見合わない |

## 結果 / 影響

- クライアントは `@supabase/supabase-js` の `from()` を直接使う。
  この呼び出しは frontend の `infrastructure/` 層に閉じ込め、画面から直接呼ばない。
- **クライアント側で `eq('user_id', ...)` を書かない**。RLS が絞るため冗長であり、
  「書き忘れたら漏れる」という誤った前提を生むため。
- RLS のポリシーが実質的な API 仕様になる。ポリシー変更はクライアントに影響しうるので、
  `docs/db-schema.md` §4 を正典として維持する。
- 見直しのトリガー: 集計やランキングなど、RLS だけでは表現できない読み取りが必要になったとき。
