# ADR-0007: DeepSeek のモデルは deepseek-chat を使う

- **状態**: Accepted
- **日付**: 2026-08-22
- **フェーズ**: 2

## 背景

類義語生成に DeepSeek API を使う。DeepSeek は対話向けの `deepseek-chat` と
推論特化の `deepseek-reasoner` を提供しており、どちらを使うか決める必要がある。
本用途は「ユーザーがボタンを押して結果を待つ」対話的な UX であり、
従量課金であるためコストも直接効いてくる。

## 決定

**`deepseek-chat` を採用する。** モデル名は `DEEPSEEK_MODEL` 環境変数で差し替え可能にし、
使用モデルを `synonym_generations.model` に記録する。

## 理由

1. **タスクの性質が合っている。** 類義語生成はモデルが持つ語彙知識の想起と整形であり、
   多段の推論・検証を要する問題ではない。reasoner の強みが働く場面ではない。
2. **レイテンシ。** reasoner は回答前に推論過程を生成するため応答が大幅に遅い。
   「単語を入れてボタンを押す」という UX では、この待ち時間が体験の質を直接下げる。
3. **コスト構造。** 従量課金は出力トークン量に強く依存する。
   reasoner は推論トークンが課金対象の出力に加算されるため、
   同じ回答を得るための出力トークンが数倍になりうる。
   （単価は変動しうるため、実際の料金は公式の料金ページで確認すること。
   ここでの主張は単価表ではなく「出力トークンが増える」という構造の話。）
4. **構造化出力の扱いやすさ。** 本設計は厳格な JSON を要求する。
   chat は JSON 出力モードをそのまま使え、パース経路が単純になる。

## 検討したが採用しなかった案

| 案 | 却下理由 |
| --- | --- |
| `deepseek-reasoner` | レイテンシとコストの増加に見合う品質差が語彙タスクでは見込めない |
| 用途で 2 モデルを併用 | MVP のユースケースが 1 つしかなく、切り替え条件を定義できない |
| 他社 LLM（OpenAI 等） | DeepSeek 利用がプロジェクトの前提条件 |

## 結果 / 影響

- プロンプト設計は JSON 出力モード前提で行う（`docs/llm-integration.md` §2）。
- `max_tokens = 600`、`temperature = 1.0` を既定とする。
- **再評価のトリガー**: ニュアンス説明の品質に対する不満が実測で確認されたとき、
  `deepseek-reasoner` との A/B を検討する。それまでは固定。
