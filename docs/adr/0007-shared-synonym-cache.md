# ADR-0007: 生成結果をユーザー横断でキャッシュする

- **ステータス**: Accepted
- **日付**: 2026-08-16
- **決定者**: Claude（設計フェーズ / Opus）

## 背景

類義語生成は LLM 呼び出しであり、1回ごとに課金される。
`happy` や `important` のような基本語は、多数のユーザーが繰り返し検索することが予想される。
生成結果を誰の単位でキャッシュするかを決める必要がある。

## 選択肢

1. **キャッシュしない** — 毎回 LLM を呼ぶ
2. **ユーザーごとにキャッシュ** — 同じユーザーが同じ単語を引いたときだけ再利用
3. **全ユーザーで共有のキャッシュ** — 同じ単語なら誰が引いても既存の結果を返す

## 決定

**選択肢3**。`words` を全ユーザー共通の辞書とし、
`synonym_generations`（+ `synonyms`）を `word_id` / `model` / `prompt_version` で引ける
共有キャッシュとする。TTL（既定90日）を超えた結果は再生成する。

## 理由

- **コスト削減の効果が最も大きい。** 単語の出現頻度はロングテールでも、
  上位の基本語に検索が集中する。ユーザー数が増えるほど選択肢2との差が開く。
- **キャッシュ内容に個人情報が含まれない。** 類義語は辞書データであり、
  誰が引いても同じ結果でよい。個人ごとに分ける理由がない。
- **レイテンシが改善する。** キャッシュヒット時は LLM を待たずに即座に返せる。
- 選択肢1は、要件の「無駄なトークン消費を避ける」に正面から反する。

## 個人情報を混ぜないための制約

この決定は「共有テーブルを認証済みユーザー全員に読ませる」ことを意味するため、
**共有テーブルにユーザー識別子を入れてはならない**。

- `synonym_generations` に `user_id` を**持たせない**（誰が引いたかは `search_history` のみが持つ）
- `search_history` は owner-only の RLS で保護する
- この制約は [`security.md`](../security.md#rls-ポリシー設計) に反映済み

## 影響

- **キャッシュの無効化手段が必要。** `prompt_version` と `model` をキャッシュキーに含めることで、
  プロンプト改訂・モデル変更時に自動的に再生成される。
- **鮮度の TTL は環境変数（`SYNONYM_CACHE_TTL_DAYS`、既定90日）で調整可能にする。**
- **同時実行時に重複生成が起きうる。** 同じ新規単語を2人が同時に引くと LLM が2回呼ばれる。
  ロックで防ぐことはせず許容する（発生頻度が低く、実害は数回分のトークン。
  ロック導入のほうが複雑さとレイテンシのコストが大きい）。
- ユーザーから見て「他人が生成した結果」が返るが、内容は辞書データであり体験上の差はない。
- 失敗（`status='failed'`）はキャッシュしない。
  存在しない単語を繰り返し引かれた場合は毎回 LLM を呼ぶことになるが、
  この経路はレート制限（失敗もカウント対象）で抑える。
