# ADR-0001: モノレポとし、直下を frontend/ と backend/ に分割する

- **状態**: Accepted
- **日付**: 2026-08-22
- **フェーズ**: 1

## 背景

フロントエンド（Expo）とバックエンド（Supabase）を単一リポジトリで管理するか、
分割するかを決める必要がある。両者はランタイム（Metro / Deno）もデプロイ先
（Vercel / Supabase）も異なる。

## 決定

単一リポジトリ（モノレポ）とし、リポジトリ直下に `frontend/` と `backend/` を置く。
npm workspaces などのツールによるパッケージ統合は**行わない**（単なるディレクトリ分割に留める）。

## 理由

- API の契約（Edge Function のリクエスト / レスポンス）がフロントとバックの両方に影響する。
  1 つの PR で両側の変更とドキュメント更新を完結させられることの価値が大きい。
- MVP の規模では、リポジトリを分けたときのバージョン整合コスト（どのフロントが
  どのバックエンドと組むか）が明らかに割に合わない。
- ワークスペース統合をしないのは、Deno と Metro という異質なランタイムを
  1 つの依存解決に押し込む必要がないため（[ADR-0002](./0002-no-shared-package-for-now.md) 参照）。
  Vercel の Root Directory 指定により `backend/` はフロントのビルドから自然に除外される。

## 検討したが採用しなかった案

| 案 | 却下理由 |
| --- | --- |
| フロント / バックでリポジトリを分割 | API 契約変更が 2 リポジトリにまたがり、レビューと追跡が困難になる。MVP の規模に対して過剰 |
| Turborepo / Nx などのモノレポツール導入 | ビルド対象が実質 2 つしかなく、キャッシュやタスクグラフの利益が出ない。学習・設定コストのみが残る |
| `apps/` `packages/` の 2 階層構成 | 階層が 1 段深くなるだけで、`apps/` に入るものが 2 つしかない。直下配置の方が読みやすい |

## 結果 / 影響

- Vercel の Root Directory は `frontend` に固定される。
- Supabase CLI は `backend/` から実行する。
- 見直しのトリガー: アプリが 3 つ以上（管理画面など）に増えたとき、`apps/` 階層の導入を再検討する。
