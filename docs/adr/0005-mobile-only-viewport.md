# ADR-0005: デスクトップ画面幅向けのレイアウト分岐を実装しない

- **状態**: Accepted
- **日付**: 2026-08-22
- **フェーズ**: 1

## 背景

Web/PWA 版は Vercel から配信されるため、デスクトップブラウザからもアクセスできてしまう。
一方で本アプリの主戦場は iOS ネイティブアプリであり、
Web 版もモバイルブラウザからのアクセスのみを想定している。

## 決定

**UI はモバイル幅（〜480px 程度）のみを対象に設計・実装する。**
デスクトップ画面幅向けのレイアウト最適化は行わない。
デスクトップブラウザで開かれた場合は、`maxWidth: 480` のコンテナで
モバイルレイアウトをそのまま中央寄せ表示するに留める。

**メディアクエリや `useWindowDimensions` による大画面向けレイアウト分岐は実装しない。**

## 理由

- 想定ユーザーの導線が「App Store からインストール」または「モバイルブラウザで開く」であり、
  デスクトップは対象外。存在しない需要に実装コストを払わない。
- **分岐を 1 箇所でも作ると波及する**。「大画面ではどう見えるべきか」を
  以降すべての画面・すべてのコンポーネントで考える必要が生まれ、
  レビュー観点も QA 対象も倍になる。MVP のスコープに対して割に合わない。
- 中央寄せの固定幅表示であれば、デスクトップで開かれても「壊れている」とは見えない。
  最低限の考慮としてはこれで十分。

## 検討したが採用しなかった案

| 案 | 却下理由 |
| --- | --- |
| デスクトップ専用レイアウトを作る | スコープ外。実装・保守コストに見合う利用が想定されない |
| デスクトップアクセスをブロックして案内を出す | 使えるものを使えなくするだけで、価値を生まない |
| 幅に応じて段階的にレスポンシブ対応 | 上記「分岐が波及する」問題をそのまま抱え込む |

## 結果 / 影響

- フェーズ 4（フロントエンド設計）では、画面設計・スタイリングをモバイル幅前提で行ってよい。
  迷ったら「モバイル幅だけ考える」が正しい判断。
- ホバー前提の UI（ツールチップ等）を作らない。タップ操作のみを前提とする。
- 見直しのトリガー: デスクトップからのアクセスが実利用の相当割合を占めることが
  実測で判明したとき。それまでは再検討しない。
