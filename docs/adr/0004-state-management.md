# ADR-0004: サーバー状態は TanStack Query、クライアント状態は Zustand

- **状態**: Accepted
- **日付**: 2026-08-22
- **フェーズ**: 1

## 背景

MVP で管理する状態は「認証セッション」「類義語生成の進行状態」「検索履歴」の 3 つ。
このうち後者 2 つはサーバー由来のデータである。

## 決定

- **サーバー状態**: `@tanstack/react-query`
- **クライアント状態**: `zustand`（認証セッションと最小限の UI 状態のみ）

## 理由

- 本アプリの状態はほぼ全てがサーバー由来であり、必要なのは
  「キャッシュ・再取得・ローディング・エラー」の状態機械。これを自前で書くと必ず穴が出る。
- 類義語生成は `useMutation` にそのまま乗る。リトライ UX（`isPending` / `error` /
  エラーコードによる出し分け）を宣言的に書ける。これは
  [`api-spec.md`](../api-spec.md) のエラーハンドリング要件と直結する。
- 認証セッションは「グローバルだが小さく、更新頻度が低い」状態で、
  Supabase の `onAuthStateChange` の購読結果を流し込むだけで足りる。
  Zustand なら Provider の入れ子を増やさずに実現できる。

## 検討したが採用しなかった案

| 案 | 却下理由 |
| --- | --- |
| Redux Toolkit | Redux が解決する問題（複雑な状態遷移、時間軸デバッグ、大規模チーム規約）が本 MVP に存在しない。ボイラープレートのみが残る |
| React Context のみ | サーバーデータのキャッシュ・再取得・失効を自前実装することになり、結局 TanStack Query の劣化版を書く |
| Jotai / Recoil | Zustand で足りる規模。細粒度の atom 分割が必要な複雑さがない |

## 結果 / 影響

- 「サーバーから来たデータを Zustand に写す」ことを禁止する。二重管理になり同期がずれるため。
  サーバーデータの参照は常に TanStack Query 経由とする。
- 見直しのトリガー: ロールプレイ会話機能で複雑なクライアント側状態機械が必要になったとき。
