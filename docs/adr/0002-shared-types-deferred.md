# ADR-0002: 共通型パッケージ（`packages/shared`）を MVP では作らない

- **ステータス**: Accepted
- **日付**: 2026-08-16
- **決定者**: Claude（設計フェーズ / Opus）

## 背景

`frontend/` と `backend/` の両方で、同じ形のデータ（類義語生成の
リクエスト/レスポンス、DB の行）を扱う。
共通型を `packages/shared` に置くか、両側でそれぞれ定義するかを決める必要がある。

## 選択肢

1. **`packages/shared` を作る** — 型を1箇所で定義し、両側から import する。
2. **両側でそれぞれ定義し、`docs/api-spec.md` を契約の単一の正とする。**
3. OpenAPI スキーマから両側の型を生成する。

## 決定

**選択肢2**。MVP では `packages/shared` を作らない。
DB の行型は両側で `supabase gen types typescript` により**生成**する（手書きしない）。

## 理由

- **共有対象が小さい。** MVP のエンドポイントは1本、共有される型は
  リクエスト1つ・レスポンス1つ・エラーコードの列挙のみ。合計で数十行。
- **参照コストが高い。** `backend/` は Deno、`frontend/` は Metro バンドラで、
  モジュール解決の仕組みが異なる。両者から解決できる共有パッケージを整えるには、
  Deno の import map と Metro の `watchFolders` / `extraNodeModules` の両方に手を入れる必要がある。
  数十行の型のために、2つのビルド設定に恒久的な複雑さを持ち込むことになる。
- **DB 型は生成物なので、そもそも共有する必要がない。** 同じスキーマから両側で生成すれば内容は一致する。
  共有パッケージにコミットすると「生成物をコミットするか」という別の問題が増える。
- **選択肢3（OpenAPI）は現状オーバーキル。** エンドポイント1本に対してスキーマ管理と
  コード生成のパイプラインを敷くのは割に合わない。

## 影響

- **リスク**: フロント/バックの型が独立して変更されると、実行時まで不整合に気づけない。
  これを緩和するために:
  - [`api-spec.md`](../api-spec.md) を契約の単一の正とし、変更時は同一 PR で両側を更新する
  - Edge Function 側は `zod` でリクエストを実行時検証し、契約違反を 400 で明示的に返す
  - E2E テスト（Phase 6、実 API 接続）で契約の整合を実際に検証する
- **再検討のトリガー**（いずれかを満たしたら `packages/shared` を導入する）:
  - Edge Function のエンドポイントが3本以上になった
  - フロント/バックの型不整合に起因するバグが1件でも発生した
  - 共有したいドメインロジック（単なる型ではなく、正規化ルールなどの実装）が生じた
    — 例: 単語の正規化ロジックを両側で持つ必要が出た場合
