# ADR-0010: 状態管理はグローバルストアを導入せず、性質ごとに道具を分ける

- **ステータス**: Accepted
- **日付**: 2026-08-18
- **決定者**: Claude（設計フェーズ / Opus）

## 背景

React Native アプリの状態管理方針を決める必要がある。
扱う状態は、認証セッション、類義語の生成結果、検索履歴、フォーム入力、UI の開閉。

このアプリの特徴として、**サーバ呼び出しの一部（類義語生成）に課金が発生する**。
そのため「いつ通信が起きるか」を制御できることが、状態管理の選定基準に含まれる。

## 選択肢

1. **Redux Toolkit（+ RTK Query）** — 単一ストアに集約
2. **Zustand + TanStack Query** — 軽量ストアとサーバ状態の分離
3. **React Context（認証のみ）+ TanStack Query + ローカル state** — グローバルストアなし

## 決定

**選択肢3。** グローバルストア（Redux / Zustand）は導入しない。

| 状態の種類 | 道具 |
| --- | --- |
| 認証状態 | React Context（`AuthProvider`） |
| サーバ状態 | TanStack Query |
| フォーム状態 | react-hook-form + zod |
| UI 状態 | `useState` |

## 理由

- **グローバルに持つ必要がある状態が、認証セッション1つしかない。**
  それ以外はサーバ状態（TanStack Query が持つ）か画面ローカルの状態であり、
  ストアに入れる動機がない。1つの状態のために Redux/Zustand を入れるのは、
  設定と規約の学習コストに見合わない。
- **認証セッションの単一の真実は `supabase-js` が持っている。**
  Context はそれを購読して配るだけでよく、ストアに複製すると二重管理でズレる。
- **TanStack Query は「いつ通信するか」の制御を宣言的に書ける。**
  これがコスト管理に直結する。特に:
  - 類義語生成を `useMutation` にすることで、**画面復帰やフォーカスによる自動再フェッチが起きない**
    （`useQuery` にすると勝手に再実行され、そのたびに課金されうる）
  - リトライ対象と回数を `QueryClient` 1箇所で制御でき、各画面に散らばらない
- Redux Toolkit（選択肢1）は、この規模では定型コードが利益を上回る。
  RTK Query を使うにしても、`useMutation` 相当の制御は TanStack Query と同等で、
  追加の抽象を持ち込む理由がない。

## 影響

- 認証状態は `AuthProvider` が `onAuthStateChange` を購読する形になり、
  **セッション失効（401）の扱いが1箇所に集まる**。各画面で 401 を扱わない。
- サインアウト時に `queryClient.clear()` を呼ぶ必要がある
  （前のユーザーのキャッシュが残らないよう、クエリキーにも `userId` を含める）。
- **再検討のトリガー**（いずれかを満たしたら Zustand の導入を検討する）:
  - グローバルに共有したいクライアント状態が3つ以上になった
  - Context の再レンダリング範囲が原因のパフォーマンス問題が実測で確認された
  - 複数の feature が同じ一時状態を読み書きするようになった
- Redux を選ばなかったため、Redux DevTools による時系列デバッグは使えない。
  代わりに TanStack Query Devtools と、Edge Function が返す `requestId` による
  サーバログとの突き合わせで調査する。
