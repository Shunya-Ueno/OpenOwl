# ADR-0016: 単体テストは外部 I/O を持たない純粋ロジックに限り、コンポーネントテストを書かない

- **状態**: Accepted
- **日付**: 2026-08-23
- **フェーズ**: 6

## 背景

本プロジェクトは**モック / スタブ / ダミーデータの使用を禁止**している
（[CLAUDE.md](../../CLAUDE.md)、[roadmap.md](../roadmap.md)）。
この禁止は、一般的なテストピラミッドの**中間層を丸ごと成立させなくする**。

- リポジトリ実装（`SupabaseTermRepository` 等）を単体テストするには
  Supabase クライアントを差し替える必要がある → テストダブル
- `DeepSeekClient` を単体テストするには `fetch` を差し替える必要がある → テストダブル
- `GenerateSynonymsUseCase` を単体テストするにはポートの偽実装が必要 → テストダブル
- React コンポーネントを Testing Library で試すにはレンダラを差し替える必要がある → 実物ではない

さらに、`architecture.md` §4 と `llm-integration.md` §5 は
**「ポート（`interface`）はテストダブル差し替えのために存在しない」**と明示している。
フェーズ 6 でこの原則を曲げるか否かを決める必要があった。

## 決定

1. **単体テストの対象を、外部 I/O を持たない純粋ロジックに限定する。**
   具体的には正規化規則、入力バリデーション、エラー → HTTP の写像、
   プロンプト組み立て、レスポンスのパース。
2. **コンポーネントの単体テストを書かない。** 画面の挙動は Web の E2E が受け持つ。
3. **カバレッジ閾値を CI で強制しない。**

## 理由

- 原則を曲げないため。「テストのときだけポートを偽実装に差し替える」を一度許すと、
  ポートの存在理由が事後的に書き換わり、`architecture.md` の記述が嘘になる。
- 純粋ロジックのテストは**モックを必要としない**。`Term.fromInput('  Improve  ')` は
  外部と一切話さない。ここには方針との衝突が存在しないので、遠慮なく厚く書ける。
- そして、この層こそテストの価値が高い。`Term` の文字種制限は
  **プロンプトインジェクション対策の主軸**であり（[security.md](../security.md) §3）、
  `mapDomainErrorToHttp` は [api-spec.md](../api-spec.md) §2.5 の表そのものである。
  仕様が表で書かれているものは、表としてテストできる。
- コンポーネントテストを捨てられるのは、**Web の E2E が実ブラウザで実バンドルを動かす**ため。
  Testing Library で得られる情報は E2E の部分集合であり、
  E2E が PR ごとに走る以上、二重に持つ意味が薄い。
- カバレッジ閾値を置かないのは、対象を絞る設計上、全体カバレッジが構造的に低くなるため。
  閾値を置けば「数字を上げるためのテスト」＝ 方針違反のモックテストを誘発する。

## 検討したが採用しなかった案

| 案 | 却下理由 |
| --- | --- |
| テストのときだけポートを偽実装に差し替える | モック禁止の直接的な違反。`architecture.md` §4 / `llm-integration.md` §5 の記述と矛盾する |
| ローカルの Supabase（`supabase start`）に対して統合テストを書く | 「実サービス」ではあるが、Edge Function の Secrets・DeepSeek 接続・本番同等の Auth 設定を CI 上で揃える手間が大きい。同じ労力を E2E に振る方が守れる範囲が広い |
| Testing Library でコンポーネントテストを書く | レンダラが実物ではない。E2E の部分集合しか得られない |
| カバレッジ閾値（例: 80%）を CI で強制する | 対象を絞る設計と噛み合わず、方針違反のテストを誘発する |

## 結果 / 影響

- テストが**存在しない**層がある: リポジトリ実装、`DeepSeekClient`、ユースケース、
  React コンポーネント。これらの正しさは E2E だけが担保する。
  **したがって E2E を落としたまま放置してはならない**。E2E がこの構成の唯一の安全網である。
- 逆に、純粋ロジックに切り出せる処理は積極的に切り出す価値がある
  （切り出せばテストできる層に移る）。新しいロジックを書くときの指針にする。
- バックエンドは Deno 標準の `Deno.test`、フロントエンドは Vitest を使う。
  どちらもテストランナーであってモックライブラリではない。
  Vitest の `vi.mock()` / `vi.fn()` は**使わない**。
- 見直しのトリガー: E2E で検出できない不具合が繰り返し発生し、
  その原因が「テストされていない中間層」に集中していると判明したとき。
