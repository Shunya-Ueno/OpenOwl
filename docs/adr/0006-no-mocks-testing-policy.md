# ADR-0006: モックを使わないテスト方針とその運用

- **ステータス**: Accepted
- **日付**: 2026-08-16
- **決定者**: Claude（設計フェーズ / Opus。方針自体はプロジェクト要件として確定）

## 背景

「実装・テストともにモック（ダミーデータ、モック API、スタブ実装）を使わない。
Supabase・Gemini API とは常に実接続する」がプロジェクト要件として確定している。
一方で設計上は `SynonymGenerator` / `SynonymRepository` といった interface を定義しており、
これは一般に「テスト用フェイクの差し込み口」として使われる。
**この方針と設計の関係を明文化しないと、実装フェーズでフェイク実装が混入する。**

## 決定

1. **フェイク／スタブ／モックのクラスを一切実装しない。** ポート（interface）の実装は
   本番で使う具象クラスのみとする。
2. **interface を定義する目的は「プロバイダの差し替え」に限定する**（Gemini → 他モデル、Supabase → 他基盤）。
   テスト容易性は interface を作る理由にしない。
3. テストは**テスト専用の Supabase プロジェクト**と**実 Gemini API キー**に対して実行する。
4. テストデータはテスト内で作成し、終了時に削除する（プロジェクトを共有するため）。

## 理由

- 要件として確定している。加えて、この方針には実利がある:
  - Gemini の応答形式・エラー挙動・レート制限は、モックでは再現できない部分にこそ問題が出る
  - RLS はモックでは一切検証できない。**実 Postgres に対して実際のトークンで叩かないと、
    ポリシーの穴は見つからない**（本プロジェクトの認可の根拠は RLS なので、これは致命的）
- 「テストのための抽象化」を禁じることで、ポートの数が最小に保たれ、設計が単純になる。

## 影響とその扱い

| 影響 | 対応 |
| --- | --- |
| テスト実行に実 API コストがかかる | Flash-Lite は低コスト。テストで使う単語を固定し、キャッシュが効く設計にすることで呼び出し回数を抑える。CI では E2E をプッシュごとではなく PR 単位で実行する（Phase 6 で決定） |
| テストが外部障害で落ちうる | 一過性の失敗と本当の失敗を区別できるよう、失敗時のエラーコードを検証する。CI の再実行で復旧するものは再実行で対応する |
| テストが遅い | ローカルの Postgres/Auth は `supabase start` のローカルスタックを使い高速に回す。Gemini だけは実接続 |
| テストデータの残留 | 各テストが自分で作った行を後片付けする。テスト用プロジェクトは定期的にリセットする |
| シークレットの取り扱い | テスト用の Supabase プロジェクトと Gemini キーを本番と分離し、GitHub Actions の Secrets に登録する（登録作業はオーナー。Phase 6 で設計） |

## 補足: 「モック禁止」が意味しないこと

- テスト用の**別プロジェクト・別 API キー**を使うことは、モックではない（推奨）。
- テスト内で**実際にユーザーを作成する**ことは、モックではない（推奨）。
- 実際の応答を**検証する**ためのアサーションは当然必要。ただし LLM の出力は非決定的なため、
  「`synonyms` が3件以上あること」「各 `term` が英字であること」のように
  **構造とスキーマを検証**し、特定の語が返ることを期待しない。
